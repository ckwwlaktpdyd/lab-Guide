# Lab Guide MVP 기획서 v2
*(Claude Code 핸드오프용 통합 문서 — v1 기획서 + 확정 스펙 병합본)*

- 원본 레포: https://github.com/ckwwlaktpdyd/lab-Guide
- 원본 데모: https://lab-guide-d1by.vercel.app/client_home.html
- 목적: 포트폴리오용 MVP. 기존 결과물은 시험 단계 레퍼런스로 취급하고, 톤앤매너를 포함해 사실상 개편에 가깝게 재설계한다.
- 관련 시각 자료: `client-portal-hifi.html`, `manufacturer-console-hifi.html`, `design-tokens.html`

## 1. 프로젝트 개요

Buffer 제조 QC 프로세스를 관리하는 서비스. 두 역할이 존재한다.

- **의뢰자(Client)**: 버퍼 제조를 의뢰하고, 진행 상황을 확인하며 제조 결과를 리뷰·서명한다.
- **제조자(Manufacturer)**: 의뢰를 수락/반려하고, 실제 공정을 진행·기록하며 결과를 1차 검토한다.

## 2. 스코프 원칙

- MVP 우선. 완성도 있는 핵심 플로우 하나를 끝까지 다듬는 것이 화면 개수를 늘리는 것보다 우선.
- **카메라/QR 스캔 기능은 스코프에서 완전히 제외.** (Safari/iOS는 BarcodeDetector API 미지원)
- **실제 계측기 연동(BLE/시리얼)도 스코프 외.** 단, 데이터 모델과 UI는 계측기 자동 수집을 전제로 설계하고 시드 데이터로 시연한다. (§9 참고)
- 장비 관리(Equipment) 화면은 Phase 2 후보로 보류.

## 3. 사이트 구조 — 완전 분리형

의뢰자와 제조자를 **별도의 두 사이트(두 개의 독립 MVP)**로 분리한다. B2B의 "고객 포털 vs 내부 운영 콘솔" 분리 패턴 참고.

| 사이트 | 플랫폼 | 사용 맥락 |
|---|---|---|
| 의뢰자 포털 (Client Portal) | 웹 / 모바일 반응형 | 사무실 책상, 다양한 디바이스에서 리뷰 |
| 제조자 콘솔 (Manufacturer Console) | 아이패드 미니 **가로 모드 전용** | 실습실 현장, 즉시 조작 |

- 제조자 콘솔은 웹 기반이므로 기기 회전을 막을 수 없음 → **세로 감지 시 "가로 모드로 돌려주세요" 안내 오버레이** 표시
- 리뷰어 혼선 방지를 위해 가벼운 랜딩/스위처 페이지 추가

## 4. 기술 스택 & 아키텍처 *(확정)*

| 영역 | 선택 | 사유 |
|---|---|---|
| 프레임워크 | Vite + React + TypeScript | SSR 불필요, Next.js보다 가볍고 Claude Code 작업에 수월 |
| 스타일 | Tailwind CSS | 공유 디자인 토큰을 config 하나로 정의, 두 사이트가 preset 상속 |
| 백엔드/DB | Supabase (무료 티어, Postgres) | 서버 코드 없이 두 사이트 연동 |
| 실시간 연동 | Supabase Realtime 구독 | 상태 변경이 상대 사이트에 즉시 반영 — 리뷰 체인 시연의 핵심 |
| 인증 | Supabase Auth (이메일 매직링크) | MVP에 충분. role은 User 테이블에서 관리 |
| 패키지 관리 | pnpm 모노레포 | 사이트 분리 구조 대응 |
| 배포 | Vercel 프로젝트 2개 | 사이트별 독립 배포 |

> ⚠️ **개정(2026-08-01)** — pnpm 모노레포 구조는 폐기했다. **단일 Vite + React 프로젝트**에서 두 앱을 라우트로 분리한다.
> 포트폴리오 MVP 규모에 workspace 경계는 관리 비용만 늘리고, 두 앱이 어차피 같은 Supabase 프로젝트를 쓰므로 패키지로 갈라둘 실익이 없다.
> 배포도 Vercel 프로젝트 1개로 줄인다. 아래 표의 "패키지 관리 / 배포" 행은 이 개정으로 대체된다.

```
/src
  /apps
    /client     # 의뢰자 포털 (반응형 웹)
    /console    # 제조자 콘솔 (아이패드 미니 가로 전용)
  /shared
    /ui         # 공유 디자인 토큰 + 공통 컴포넌트
    /db         # Supabase 클라이언트, 타입, 쿼리 헬퍼
  /routes.tsx   # 두 앱 + 랜딩/스위처
```

- 두 사이트가 **동일한 Supabase 프로젝트**를 공유 → 상태 연동에 별도 API 서버 불필요
- 목업 데이터는 **시드(seed) 데이터**로 전환: 데모 계정, 단계별 배치 샘플, 계측기 자동 기록 값 포함
- **RLS(Row Level Security)**로 역할별 접근 제어 — §6 권한 매트릭스를 DB 레벨에서 강제

## 5. 디자인 시스템 *(확정)*

### 컨셉
Merck 2015 리브랜딩의 방향성(생동감·유기적 모티브·모노스페이스 데이터·기술 그리드)을 **pH 지시약 스펙트럼**으로 재해석. 팔레트가 도메인에서 직접 유래하므로 브랜드 컬러가 곧 상태 컬러가 된다. *(Merck의 로고·브랜드 컬러 코드는 사용하지 않는다.)*

### 컬러
| 토큰 | 값 | 유래 / 용도 |
|---|---|---|
| `indicator-amber` | `#F0A62E` | BTB 산성 — 대기 / 주의 |
| `indicator-green` | `#3AA05F` | BTB 중성 — 완료 / 서명 |
| `indicator-teal` | `#0E8290` | BTB 염기 — 진행중 / **프라이머리** |
| `phenol-pink` | `#E14E68` | 페놀프탈레인 — 편차 / 반려 / 재제조 |
| `ink` `#17272B` / `ink-soft` `#5C6B70` / `line` `#D4DCDD` | | 뉴트럴 |
| `surface` `#FFFFFF` / `paper` `#FAFAF8` / `bench` `#EEF2F2` | | 카드 / 의뢰자 배경 / 제조자 배경 |

- **시그니처**: 진행률 표현(스테퍼·타임라인)에 amber→green→teal 그라디언트. "적정이 진행될수록 색이 변한다"는 도메인 은유. 유일한 장식 요소로 제한.
- 그림자 없음(플랫). 계층은 1px 보더 + 배경 대비로 표현.
- 라운드: 카드 12 / 버튼·입력 8 / 배지 6 / 칩 999

### 타이포그래피
- UI: **Pretendard Variable** (본문 400, 강조 600, 헤딩 700–800)
- 데이터: **JetBrains Mono** — LOT 번호, 측정값, 타임스탬프
- 숫자는 `tabular-nums` 적용
- 스케일: display 26/800 · title 19/700 · body 15/400 · caption 12.5/400 · data 15(mono, KPI 32)

### 스킨 분기
- **의뢰자 포털**: `paper` 배경, 섹션 간격 40–48, 카드 패딩 24 — 여백 넉넉, 신뢰·투명성 톤
- **제조자 콘솔**: `bench` 배경 + 다크 아이콘 레일, 섹션 간격 24, 카드 패딩 16, **터치 타겟 최소 44pt** — 정보 밀도·속도 우선
- 다크 모드(제조자)는 Phase 2. MVP에선 토큰 구조만 준비.

## 6. 역할 및 권한 매트릭스

| 기능 영역 | 의뢰자(Client) | 제조자(Manufacturer) |
|---|---|---|
| 대시보드 | 본인 의뢰 건 조회 | 담당/전체 배치 현황 조회 |
| 신규 의뢰 | 생성 가능 | 수락/반려 처리 |
| 재의뢰 | 코멘트 등록 후 재의뢰 | 수락/반려 처리 |
| **재제조 요청** | **요청 가능 (사유 필수)** | **수락/반려 처리** |
| 공정 진행 | 조회만 | 단계별 업데이트, 완료 처리 |
| 이슈/편차 | 열람, 코멘트 | 등록, 원인·조치 입력, 상태 추적 |
| 배치 요약 | 조회 | 작성/확정 |
| 결과 | 조회, **리뷰·서명** | 입력, **1차 검토(서명)** |
| 준비 가이드 | 조회 | 조회 + 체크리스트 |
| 장비 (Phase 2) | 조회만 | 상태/점검 이력 관리 |

**용어 확정**: 제조자 = *1차 검토(서명)*, 의뢰자 = *결과 리뷰(서명)*. 결재 승인이 아니라 **수기 버퍼 기록지를 의뢰자가 직접 확인하고 서명하던 실제 관행의 디지털 대응**이다. "승인"이라는 표현은 사용하지 않는다.

## 7. 상태 플로우

```
의뢰 등록
  → 제조자 수락/반려
      ├─ 반려 → 의뢰자 코멘트 → 재의뢰 → (수락/반려로 복귀)
      └─ 수락 → 배치 생성 → 공정 진행
                  ├─ 편차 발생 → 편차 등록/조치 → 공정 진행 복귀
                  └─ 공정 완료 → 배치 요약 작성
                                → 결과 입력 + 제조자 1차 검토(서명)
                                    → 의뢰자 결과 리뷰
                                        ├─ 보완 요청 → 제조자 재작업
                                        └─ 리뷰 서명 → 완료
                                                        │
                        ┌───────────────────────────────┘
                        ↓
                 재제조 요청 (사유 필수)
                   → 신규 의뢰로 진입, 원본 의뢰와 링크
```

**재제조 요청**: 버퍼가 100% 정확도로 만들어지지 않아 실험 단계에서 문제가 드러나는 경우가 있다. 따라서 재제조 요청은 리뷰 대기 상태뿐 아니라 **완료된 의뢰에서도 접근 가능해야 한다.** 요청 시 `parent_request_id`로 원본과 연결되고, 제조자 콘솔에서 원본 배치 결과가 대조용으로 함께 표시된다.

## 8. 화면 리스트 — 의뢰자 포털 *(통합 후 5장)*

v1의 화면 3~6(공정 조회/이슈/배치 요약/결과)은 **"의뢰 상세" 한 페이지로 통합**한다. 좌측 타임라인이 스토리 축, 우측이 문서·액션.

| # | 화면 | 핵심 기능 |
|---|---|---|
| 1 | 대시보드 | 본인 의뢰 현황. 미니 그라디언트 스테퍼로 단계 표시, 액션 필요 건 상단 고정 |
| 2 | 새 의뢰 | 레시피 선택 → 타겟 파라미터 자동 채움, **희망 완료 일시(날짜+시각)** 입력 |
| 3 | 의뢰 상세 | 타임라인 + 제조 결과 + 코멘트 + 리뷰 서명 / 보완 요청 / 재제조 요청 |
| 4 | 캘린더 | 예약 생성·조회 |
| 5 | 준비 가이드 | 공유 화면 |

- 상단 내비: 내 의뢰 / 캘린더 / 준비 가이드 + `+ 새 의뢰` CTA
- 의뢰 상세 액션 배치: [리뷰 완료·서명] [보완 요청] 을 한 줄, **구분선 아래 [↻ 재제조 요청]** 별도 배치(새 배치를 생성하는 무게가 다른 액션이므로 오조작 방지)
- 편차 발생 시 타임라인에 pink 항목으로 삽입 → 탭하면 원인·조치 열람 + 코멘트

## 9. 화면 리스트 — 제조자 콘솔

**글로벌 프레임**: 다크 아이콘 레일(~88pt) + 리스트(~320pt) + 상세 패널(~730pt) 스플릿뷰. 레일 5항목(홈/의뢰/배치/편차/장비), 의뢰·편차에 미처리 건수 배지.

| # | 화면 | 핵심 기능 |
|---|---|---|
| 1 | 로그인 | 역할 인증 |
| 2 | 대시보드 | KPI 3개(신규 의뢰 대기=amber / 진행중 배치=teal / 미해결 편차=pink) + "처리 필요" 큐. 조회용이 아닌 **작업 진입점** |
| 3 | 의뢰함 | 신규·재의뢰·재제조 수락/반려. 재제조 건은 사유 + **원본 배치 결과 대조 표시** |
| 4 | 배치 목록 | 상태 필터, 진행 단계 표시 |
| 5~8 | **배치 상세** | 탭 4개(공정/편차/요약/결과)로 통합 |
| 9 | 장비 관리 | Phase 2 후보 |

**배치 상세 규칙**
- 헤더: LOT(mono) + 상태 배지 + 타겟 파라미터 + 희망 완료 일시
- **탭 잠금**: 공정 완료 전 요약·결과 비활성(🔒), 요약 확정 전 결과 비활성 → 워크플로우 순서 강제
- 공정 탭: 세로 스텝 리스트, **현재 진행 단계에만** 입력 박스 인라인 노출
- 입력 박스 액션: [단계 완료](green) [편차 등록](pink 아웃라인) — 편차 등록이 공정 흐름 안에 있어 화면 이탈 없음
- 수락 = 배치 생성. 별도 "배치 만들기" 단계 없음
- 반려는 사유 입력 모달 필수 → 의뢰자 코멘트 스레드로 전달

## 10. 데이터 모델

> 1차 초안 + 계측기/재제조 보강분. **필드·제약조건 최종 검증은 진행 중.**

- **User**: id, name, role(client/manufacturer), org
- **Request**: id, requester_id, recipe_id, `request_type`(신규/재의뢰/**재제조**), `parent_request_id`, status(대기/수락/반려), `desired_completion_at`(**날짜+시각**), `reason`(재제조 시 필수), comments[], created_at
- **BufferRecipe**: id, name, target_params(pH, 농도, 부피 등), steps[]
- **Batch**: id, request_id, lot_number, assigned_manufacturer_id, status(준비중/진행중/편차발생/완료), start_at, end_at
- **ProcessStep**: id, batch_id, step_name, status, measurements[], updated_by, updated_at
- **Deviation**: id, batch_id, description, cause, corrective_action, status(open/resolved), created_by, resolved_at
- **BatchSummary**: id, batch_id, content, confirmed_by, confirmed_at
- **Result**: id, batch_id, values(Measurement[]), manufacturer_review{signed_by, signed_at}, client_review{status(리뷰완료/보완요청), signed_by, signed_at}

### Measurement (공통 구조)
무선 데이터 전송 계측기가 표준인 현재 실무를 반영해 측정값에 **출처** 개념을 둔다. (아날로그 출력 첨부 방식은 더 이상 사용되지 않음)

- `value`, `unit`
- `source`: `instrument` | `manual`
- `instrument_id` (자동): 예 `"pH-2000-A"`, `"COND-500"`
- `captured_at`: 자동 수집 시각
- `entered_by`, `override_reason` (수동): 입력자 + 사유 — **QC 감사 추적(audit trail)**

**UI 규칙**
- 자동 수집: teal 배경 필드 + `⚡ pH-2000-A 자동 기록 14:31` 배지, 읽기 전용
- 수동 덮어쓰기: 값 탭 → 사유 입력 필수
- 의뢰자 결과 패널에도 동일 배지 노출 (투명성 톤)
